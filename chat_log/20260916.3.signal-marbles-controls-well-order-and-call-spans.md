## Problem/Context
1. **The controls moved.** `.mb-controls` is a right-anchored flex row and `.mb-readout` was its last
   child, so the row's width was the readout's width: `18 columns . 54ms` is 130px (the `min-width`
   floor) and `column 17 of 18 . 54ms` is 144.5px, so entering a column slid all four controls
   **14.5px** left and leaving it slid them back. The toggle did the same on its own: `play` and
   `pause` are different words and `.mb-control` was sized by whichever it carried — 40.5px against
   47.1px, moving its three neighbours **6.6px** twice per play loop.
2. **A column had no order.** Lanes are separate arrays, so two events on two lanes at one column had
   no order between them in the document at all; the panel rendered lane declaration order, which is
   not the order subscriptions are lifted in.
3. **A shared lane had no entry.** `lanes.through` is *read*, never *declared*: only `declared` lanes
   get the subscribe marker (`2_run.ts`'s `scheduler.run` loop), and a `through` lane has no `birth`
   either. So a shared source appeared in **no event of the document** — which is exactly why the
   demo's column 1 showed the two inner subscriptions (`switched#1`, `merged#1`) and nothing that
   opened them. The model's own comment named the gap: "A declared lane has none: it was subscribed
   before the run started."
4. **`share` is a lift shape, not a detail.** `through` pipes `share()` internally, so one subscription
   feeds every lane derived from it; its window opens on the first reader and closes when the last one
   leaves (`resetOnRefCountZero` default). The order of *joins* is part of the well-order.
5. **A call had no span.** `^`/`v` say a subscription started and stopped; nothing drew the stretch
   between, so "who was called first" and the nesting of an inner's call inside its lifter's could not
   be read off the picture.

## Solution/Approach
**The controls: take the buttons out of the variable-width row's budget.** `.mb-head` is now
`title | readout | controls` with `justify-content: flex-end`, `.mb-title { flex: 1 1 auto; min-width:
0 }` (the only thing allowed to give ground), `.mb-controls { flex: 0 0 auto }`, and `.mb-readout
{ flex: 0 0 auto; min-width: 130px; white-space: nowrap }` so small numbers cannot make it thin and it
cannot wrap. The toggle gets one box for both labels: `.mb-control[data-act="toggle"] { box-sizing:
border-box; inline-size: 52px; padding: 0 }`. Measured live: readout 130 -> 144.5 while the title goes
770.1 -> 755.6 and every control keeps the same left and width. Regression test reads each control's
box across all-revealed, a stepped column, and a playing player, and requires the readout's words and
the toggle's label to differ first (otherwise it would pass on a surface that never changes).

**The well-order: `seq`, recorded at production.** `MarbleNotificationSchema` gained an optional
`seq` — the whole-document production index, stamped by the recorder (`let produced = 0` in
`createRecorder`, both push sites). `marbleEntries(doc, tick)` reads a column back in that order and
hands each entry its `cause` (`from` where a producer wrote one, or the birth of a lane the entry
started) and its `order` — the call index within the column, 0 first. A hand-written document has no
`seq`, so lane order stands in for it, which is what a document whose lanes were declared in subscribe
order already meant. The panel is now driven by `marbleEntries` instead of `flatMap` over lanes.

**The shared lane's entry: record it where `share` opens it.** Inside `through`'s `new Observable(...)`
subscribe callback — which `share` runs exactly once, on the first reader, and again if the refcount
resets — the recorder writes `subscribe` with the note "the first reader opened this shared
subscription", before subscribing the source. Live column 1 now reads:

    column 1 at 0ms
    switchMap     subscribe  switched#1
    interval(12)  subscribe  outer#1   the first reader opened this shared subscription
    mergeMap      subscribe  merged#1

which is the lift order: the reader's own entry first, then the source its chain lifted, then the
second reader — not the structural order of the lanes.

**The call span: a bracket over whole tracks.** `marbleCallSpans(doc)` walks each lane's events: a call
opens at the lane's first event (a `subscribe` where the producer recorded one, the lane's first event
where it did not, because a hand-written lane may simply start) and closes at the first `unsubscribe`
or terminal (`error`/`complete`/`truncate`); `to: null` is a call still running. A lane subscribed,
unsubscribed and subscribed again yields two spans, because **a pair counts calls, not lanes**. The
surface draws one `.mb-span` per call as a grid item over whole tracks — `grid-column: from + 2 / span
(to - from + 1)` — the same track list the axis and every strip are laid out over, so the ends land on
columns with no new geometry (`.mb-break` is the precedent for a positioned range element). `(` and
`)` tips with a hairline between them, in a band above the marbles so nothing is covered; nested calls
read as nested brackets one lane deeper. The reveal cuts it: `applyReveal` clamps the drawn end to the
revealed column and sets `data-open`, which hides the closing tip, so an unfinished call (or one the
reveal has not reached the end of) is drawn without a `)` the document does not have.

## Key Insights
- **A `through` lane was in no event at all.** Not declared (no subscribe marker), not born (no
  `birth`): the two ways a lane can enter the document both missed it, so a shared source was invisible
  while everything read through it was not. The fix is at the one moment it does enter a state —
  `share`'s connect on the first reader.
- **Lanes are arrays, so a document had no cross-lane order.** Order is decided once, at production;
  `seq` is that decision written down, and `marbleEntries` is the read side. Lane declaration order was
  only ever an approximation of it.
- **A lane that gains an entry renumbers the values after it.** `outer#1` is the subscribe now, and the
  values moved to `#2`/`#3`/`#4`. Every `from` is written at run time so the document stayed
  self-consistent, but four assertions had the old ids written down; they now name the id through the
  document, which is also what they meant.
- **A right-anchored flex row behind a variable-width sibling moves.** The readout was inside
  `.mb-controls`; a text box at the end of a button row is a button row that resizes. Left of the
  buttons its growth is spent on the title's slack instead.
- **A control sized by its label is a toolbar that resizes.** `play`/`pause` are different words: one
  box for both, `box-sizing: border-box` included.
- **The grid already knows how to span.** A bracket over whole tracks is `grid-column: from + 2 / span
  n` against the same `--mb-tracks` list; no new geometry, and the geometry suite can measure it
  against `marbleAxis`'s own `x`.
- **The reveal must cut every new mark.** A `)` the reveal has not reached is a fact nobody has
  observed yet; `data-open` hides the tip rather than drawing a close the document may not have.
- **`screenshotFailures` writes into `__screenshots__` under the test's name.** A failing run leaves
  one, a clean run does not rewrite it; three were deleted this session rather than committed.
- **Reading `git push` output matters.** A fast-forward range whose old tip is 25 commits back means the
  push carried every lane's unpushed local commits, not just yours.
- **`-u` goes through the browser queue too**: `node ../../scripts/browser-queue.mjs vitest run
  --config vitest.browser.config.ts -u`, then a plain `pnpm run test:browser` to prove the stored
  reference is stable without it.
- **A measured claim can be a measurement bug.** An intermediate pass reported 42/87 edges up to 444px
  off; the born edges target a *lane id* whose anchor is that lane's `subscribe` marble, and the script
  had compared against the lane row's left edge. Re-measured against the real anchor: 0.000px.
