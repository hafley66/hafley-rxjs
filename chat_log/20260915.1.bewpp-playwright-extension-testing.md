# Session: bewpp-playwright-extension-testing

## Goal
Create a reusable Playwright implementation over BEWPP's installed Chrome extension transport, then consume the resulting stock Playwright Browser, BrowserContext, Page, Locator, and Worker objects from @hafley66/vitest-playwright node-realm tests. The same system should support testing Chrome extension pages, content scripts, and MV3 service workers.

## Current State
- `~/projects/lol/playwright-local` is a Microsoft Playwright checkout containing an extension-backed CDP relay that already implements most of the required architecture.
- `~/projects/lol/danbooru-studio/web/packages/browser-ext-worker-playwright-proxy` is the current BEWPP package. It uses an MV3 worker plus content-script message bridge and exposes a Playwright-shaped subset built with Testing Library. It lacks Playwright protocol compatibility, CDP, trusted input, network interception, browser chrome, cross-origin iframe controls, and other extension target internals.
- `~/projects/lol/danbooru-studio/web/packages/bewpp-mcp` exposes BEWPP through stdio MCP and an authenticated loopback bridge.
- `~/projects/hafley-rxjs/packages/vitest-playwright` already supplies node-realm Vitest fixtures, `$page`/`$context`, retries, logs, screenshots, traces, route/clock support, and accepts Playwright Browser/Page types.
- `~/projects/hafley-rxjs/packages/xdom` currently owns routed DOM events, layout, sizing, chords, and React containers. It has no Chrome-target or browser-lifetime ownership.
- No implementation changes were made during this planning turn.

## Problem/Context
The desired API resembles Vitest Browser and Playwright locators while controlling an existing user-selected Chrome tab through an MV3 extension. The extension service worker can be suspended, has no page DOM, and should not host the complete Playwright server. Playwright already separates its client/server protocol and injects selector machinery through CDP execution contexts.

The extension-testing requirement adds three target classes:
- Popup, options, side-panel, and extension pages map to Playwright `Page`.
- MV3 background workers map to Playwright `Worker`.
- Content-script UI is exercised through the containing `Page` and its frames/DOM.

A BEWPP controller extension should inspect a separate extension under test. Testing BEWPP's own worker through itself creates a circular lifetime because suspending or reloading that worker destroys the transport. BEWPP's own extension tests should retain an external persistent-Chromium harness.

## Solution/Approach
Use three dependency layers:

1. `@hafley66/bewpp`
   - Pairing and authentication
   - Extension WebSocket/message transport
   - User-granted tab and target access
   - Observation APIs and extension lifecycle

2. `@hafley66/bewpp-playwright`
   - Extension-backed CDP relay
   - Synthetic browser/target/session model
   - Connection through stock `playwright.chromium.connectOverCDP()`
   - Mapping of tab IDs to Page and extension IDs/target IDs to Worker
   - No custom locator implementation; preserve Playwright locator parsing, injected scripts, strictness, auto-waiting, actionability, frames, and protocol errors

3. `@hafley66/vitest-playwright`
   - Add BEWPP as a Browser source
   - Continue exposing ordinary Playwright objects
   - Add attached-context ownership semantics and extension fixtures

Proposed public types:

```ts
export type BewppTarget =
  | { kind: "page"; tabId: number; targetId: string; url: string; page: Page }
  | { kind: "service-worker"; extensionId: string; targetId: string; url: string; worker: Worker }

export type BewppPlaywrightSession = {
  browser: Browser
  context: BrowserContext
  targets: readonly BewppTarget[]
  page(tabId: number): Page
  extensionWorker(extensionId: string): Worker
  refreshTargets(): Promise<readonly BewppTarget[]>
  close(): Promise<void>
}

export function connectBewppPlaywright(
  options: {
    relayURL: string
    token: string
    clientName?: string
    tabIds?: readonly number[]
    extensionIds?: readonly string[]
  },
): Promise<BewppPlaywrightSession>
```

Generalize the relay's current tab-only model:

```ts
type RootTargetKey =
  | { kind: "tab"; tabId: number }
  | { kind: "extension"; extensionId: string }
  | { kind: "target"; targetId: string }

type TargetSession = {
  key: RootTargetKey
  sessionId: string
  targetInfo: CDPTargetInfo
  childSessions: Set<string>
}
```

Use CDP commands/events as the extension boundary. Keep locator query plans and Playwright protocol objects in the long-lived Node process. The MV3 service worker remains a thin allow-listed proxy around `chrome.debugger.attach`, `detach`, `sendCommand`, `getTargets`, and required tab operations.

For Vitest, generalize the browser source and ownership:

```ts
type BrowserSource =
  | { kind: "launch"; name: BrowserName; options: LaunchOptions }
  | { kind: "playwright-server"; wsEndpoint: string; headers?: Record<string, string> }
  | { kind: "bewpp"; relayURL: string; tokenFile: string; tabIds?: readonly number[]; extensionIds?: readonly string[] }

type ContextOwnership = "create-per-test" | "create-per-file" | "borrow-attached"
```

`borrow-attached` removes test-owned listeners, routes, bindings, clock state, and tracing on release while leaving the user's browser, context, and pre-existing tab open.

## Key Insights
- The requested distributed Page abstraction already exists in the local Playwright fork: the extension forwards Chrome debugger traffic while a server-side synthetic CDP browser turns selected tabs into genuine Playwright Pages.
- `createExtensionBrowser()` starts a CDP relay, establishes the extension connection, then calls `playwright.chromium.connectOverCDP()`.
- `BrowserModel` translates Chrome tab IDs and debugger sessions into synthetic Playwright CDP sessions and tracks worker/OOPIF child sessions.
- A Playwright Locator is a lazy `{ frame, selector }` query plan. It resolves at action time through the server and injected selector engine, so BEWPP should transport CDP rather than duplicate locator behavior.
- The MV3 service worker should remain a thin proxy because suspension destroys in-memory pending operations. The Node realm owns Playwright object identity and pending actions.
- Chrome debugger typings permit `tabId`, `extensionId`, or `targetId`, and expose `chrome.debugger.getTargets()`.
- Existing attached browser contexts require borrowed-resource semantics. Current Vitest fixtures assume they create and close contexts/pages.
- Extension worker identity is document-lifetime state. Extension ID plus target class is stable; the Worker object changes after restart.
- Testing the controller extension requires an external harness; testing a second extension can use BEWPP as controller.
